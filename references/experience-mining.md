# 经历深挖

简历上的一行字，背后通常压着一整段没被说出来的经历。

比如"参与多个客户项目的数据核对"——这一行招聘方看不出你到底做了什么：是跟着看，
还是独立完成？多少个、什么规模？你在里面遇到过什么棘手的事、怎么处理的？

**深挖就是把这些压扁的东西重新展开，存成可复用的素材。** 挖出来的东西有三个去处：

- **简历** —— 把"参与"改成有主语、有动作、有结果的 bullet（`tailoring.md` W4）
- **网申开放题** —— "最有成就感的一件事"不用现编（`webapply.md` §6）
- **面试回答** —— STAR 故事随取随用（`interview-prep.md`）

一份经历挖一次，三处都能用。这是它值得单独花时间的原因。

数据存 `resumes/experience-bank.json`（在 `resumes/*` 的 gitignore 覆盖范围内，不入库）。

## 和 insights 的分工

别搞混这两个库：

| | `state/match_insights.json` | `resumes/experience-bank.json` |
|---|---|---|
| 管什么 | **岗位匹配层**的洞察 | **经历本身** |
| 典型内容 | 哪类 JD 打分低、哪版简历过筛率差、跨岗位的教训 | 某段实习里具体做过什么、量化数字、STAR 故事 |
| 组织方式 | 扁平列表（`confirmed_facts`） | 按经历分组，每段带 facts + star_stories |
| 谁写 | `insights.py` | 本流程（AI 直接读写 JSON） |

W3 诚实性核查问出来的零散事实仍然照旧进 `insights.py add-fact`——那是"这次改简历用到的证据"。
如果那条事实明显属于某段具体经历，**顺手也往素材库里归一份**，标 `from_insights: true`。
两边都留，不互相删。

## 红线

和改简历（`tailoring.md` W3/W4）完全一致，一个字不放松：

1. **只记用户亲口说的。** 不推断、不补全、不"合理演绎"。
2. **每条素材入库前逐条复述确认。** 用户说"大概五六个人"，你记的就是"约 5-6 人"，
   不许写成"6 人团队"。
3. **数字记不清就标"约"或者干脆不记。** 绝不替用户圆一个数——面试官追问细节时,
   编出来的数字是会当场碎掉的，那比没有数字糟糕得多。
4. 用户说"这个别写进去"→ 记进 `gaps_probed` 说明问过了、不用再问，但不存内容。

## 挖掘七问法

对每段经历循环下面七问。**不是问卷，是线索**——用户答着答着自己带出别的东西，跟着走就好。

| # | 问什么 | 为什么问这个 |
|---|---|---|
| 1 | **角色边界**：这件事里哪部分是你做的、哪部分是团队/导师做的？ | 简历最容易含糊的地方。招聘方最想知道的也是这个 |
| 2 | **最难的瞬间**：整段经历里最卡的一次是什么时候？ | STAR 里的 S 和 T。故事的抓手都在这儿 |
| 3 | **决定与取舍**：当时你做了什么决定？有没有放弃掉别的选项？ | 体现判断力。"我选了 A 不选 B，因为…"比"我完成了 A"强一个量级 |
| 4 | **量化前后**：有没有数？规模、频次、耗时、错误率、覆盖面——前后对比最好 | 把形容词换成数字。**问不出来就算了，不要凑** |
| 5 | **反事实**：如果这件事没有你，会怎么样？ | 逼出真实贡献。答不上来说明这段经历确实边缘，那也是有价值的信息 |
| 6 | **能力证明**：这段经历能证明你会什么？ | 直接对应 JD 的能力项，改简历时按这个索引取材 |
| 7 | **可展示的证据**：有没有留下什么东西？报表、模型、文档、作品、评价 | 面试可以带、可以聊；也提醒用户别把资产弄丢了 |

**节奏控制**：

- **一次只挖一段经历**，5-8 问封顶。挖到用户开始答"记不清了""差不多吧"就停——
  那是信息枯竭的信号，继续问只会逼出编造。
- 问累了就存档，`gaps_probed` 记下问到哪、哪些没问出来，下次接着来。
- 用户答得兴起、主动多说，那就跟着听完，别打断去走流程。

## 三个触发点

**a) 改简历时定向挖（最常用）**

`tailoring.md` W3 差距分析发现 **JD 要某项能力、但简历里这块表现薄弱**时，
不要直接下结论"这是短板"——**先挖一轮再判断**。很多时候不是没做过，是没写出来。

定向挖 3-5 问（只问和这项能力相关的），挖到的当场用进这一版简历，同时入库。
挖完仍然空，才写进差距分析。

**b) 用户主动（"陪我挖挖经历""深挖一下那段实习"）**

按段全面挖，走完整七问。适合面试季开始前集中做一遍。

**c) 起草网申开放题 / 面试答案之前**

先查库。查询顺序：**素材库 → `webapply-profile.json` 的 `custom_answers` → 现场问用户**。
库里有现成 STAR 故事就直接改写成答案，别从头问。

## 数据结构

```json
{
  "schema_version": 1,
  "updated_at": "…",
  "experiences": [
    {
      "id": "acme-intern",
      "org": "…", "role": "…", "period": "…",
      "source": "resume|form|user",
      "facts": [
        { "text": "用户亲口说的事实，一句话",
          "numbers": "约 5-6 人 / 两周 / 30+ 份报表",
          "confirmed_at": "YYYY-MM-DD",
          "tags": ["抗压", "Excel", "跨部门协作"],
          "from_insights": false }
      ],
      "star_stories": [
        { "title": "两周从协助到独立交付",
          "s": "情境", "t": "任务", "a": "行动", "r": "结果",
          "best_for": ["抗压提问", "学习能力提问"],
          "confirmed_at": "YYYY-MM-DD" }
      ],
      "evidence": ["可展示的东西，如做过的模板、报表、作品"],
      "gaps_probed": ["问过团队规模，用户记不清，别再问"],
      "last_mined_at": "YYYY-MM-DD"
    }
  ]
}
```

`id` 用 kebab-case 短标识（`acme-intern`、`xyz-project`），改简历和面试排练靠它引用。

## 存档后

向用户复述一句"这轮挖到 N 条素材、M 个故事，存进 XX 那段了"，
**并说明它们接下来会在哪儿用上**——不然用户不知道刚才那十分钟换来了什么。
